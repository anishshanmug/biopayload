# BioPayload Communication MVP  
**Design Document & Engineering Guidelines**

---

## 1. Purpose

This document defines the **software design, assumptions, interfaces, and build guidelines** for the BioPayload Communication MVP. It is intended to be handed off to an engineering team to implement the system end-to-end.

The MVP enables a **Python desktop application** to directly control and monitor a **payload based on an Arduino Nano** via a wired serial connection.

---

## 2. System Overview

### High-level architecture

- **Home Computer**
  - Python GUI application
  - Operator-facing control and scheduling
  - Data logging and run management
- **Payload**
  - Arduino Nano
  - Executes experiment logic
  - Reads sensors
  - Controls temperature and challenges
  - Streams telemetry

### Communication model

- USB Serial (CDC/ACM)
- Text-based, newline-delimited messages
- Request/response with acknowledgements
- Single controller ↔ single payload

---

## 3. MVP Functional Scope

### Supported functionality

- Connect to Arduino Nano over USB serial
- Configure experiment parameters:
  - Sensor sampling rate
  - Number of challenges
  - Target temperature
- Run experiment:
  - Immediately (“Run Now”)
  - At a scheduled time (ground-side scheduling)
- Monitor experiment state
- Stream telemetry from payload
- Abort experiment safely
- Log experiment data and configuration locally

### Explicit non-goals (out of scope)

- Wireless communication
- Cloud services or networking
- Multi-payload control
- Autonomous payload scheduling
- Firmware updates
- Security/authentication
- Flight-grade reliability

---

## 4. Assumptions

### Hardware & environment

1. Payload Nano is connected via USB to the home computer
2. Single Nano per application instance
3. Stable power during experiment execution
4. Nano has sufficient RAM/CPU for parsing commands and running the experiment
5. Temperature sensing and control hardware already exists

### Time & scheduling

6. Home computer is the time authority
7. Python app remains running during scheduled experiments
8. Timing accuracy within ~1 second is acceptable

### Communication

9. Serial connection is reliable but not perfect
10. Telemetry data rate fits within serial bandwidth
11. Text-based JSON messages are sufficient
12. Commands are sent sequentially, not concurrently

### Software behavior

13. Nano implements a clear internal state machine
14. Configuration is immutable once the experiment starts
15. Nano validates all inputs independently
16. Only one operator controls the system at a time

### Data & safety

17. Home computer is the system of record for data
18. Telemetry loss is acceptable for MVP
19. Abort command always places payload in a safe state
20. Occasional failure is acceptable (prototype-level reliability)

---

## 5. User Workflows

### Run Now

1. Launch GUI
2. Select serial port and connect
3. Set experiment configuration
4. Validate configuration
5. Click **Start**
6. Monitor telemetry and state
7. Experiment completes and data is saved

### Scheduled Run

1. Connect to payload
2. Configure experiment
3. Select future date/time
4. Arm schedule
5. GUI waits until scheduled time
6. GUI sends `START`
7. Experiment executes and logs are saved

### Abort

- Operator clicks **Abort**
- GUI sends `ABORT`
- Payload transitions to safe IDLE state
- Logs are finalized

---

## 6. Experiment Configuration Model

Each experiment is defined by a configuration object:

| Field | Type | Description |
|------|-----|-------------|
| `sample_rate_hz` | float | Sensor sampling frequency |
| `num_challenges` | int | Number of challenges to run |
| `target_temp_c` | float | Target temperature in °C |
| `run_id` | string | Unique identifier generated by GUI |
| `created_at` | timestamp | Configuration creation time |

Configuration is serialized as JSON and transmitted to the Nano.

---

## 7. Communication Protocol

### Transport

- USB serial
- Baud rate: 115200
- 8N1 framing
- Newline (`\n`) delimits messages

### Message direction

- **Home → Nano:** commands and configuration
- **Nano → Home:** acknowledgements, state, telemetry, results

---

## 8. Command Set

### Home → Nano

| Command | Purpose |
|------|--------|
| `HELLO` | Handshake and connectivity check |
| `SET_CONFIG {json}` | Send experiment configuration |
| `START` | Begin experiment |
| `ABORT` | Immediately stop experiment |
| `PING` | Optional heartbeat |

### Nano → Home

| Message | Purpose |
|-------|--------|
| `ACK <cmd>` | Acknowledge successful command |
| `ERR {json}` | Command or runtime error |
| `STATE <state>` | Current payload state |
| `TELEM {json}` | Telemetry data |
| `RESULT {json}` | Experiment summary |

---

## 9. Payload State Machine

### States

- `IDLE` – Ready for configuration
- `RUNNING` – Experiment executing
- `DONE` – Experiment completed
- `ERROR` – Fault detected, safe state

### State rules

- `SET_CONFIG` only accepted in `IDLE`
- `START` only accepted in `IDLE`
- `ABORT` accepted in all states
- Errors force transition to `ERROR` then `IDLE`

---

## 10. Telemetry Model

Telemetry messages are JSON objects sent periodically:

```json
{
  "run_id": "2026-01-28T00:12:00Z",
  "t_ms": 15320,
  "temp_c": 24.7,
  "sensor": 812,
  "challenge_i": 3
}

```

### Logging rules

- All incoming telemetry is timestamped on receipt
- State transitions and errors are written to `events.log`
- Configuration is saved exactly as transmitted to the payload

---

## 12. Python Application Architecture

### Core components

- GUI thread (Tkinter or similar)
- Serial I/O thread
- Thread-safe message queue
- Scheduler / timer subsystem
- Logger subsystem

### Responsibilities

**GUI thread**
- Handle user input
- Display system state and telemetry

**Serial thread**
- Read and parse incoming messages
- Send commands to the payload

**Scheduler**
- Trigger `START` at the scheduled time

**Logger**
- Persist configuration and experiment data to disk

---

## 13. Safety & Fault Handling

### Abort behavior

- `ABORT` halts all challenges immediately
- Temperature control is disabled or set to a safe state
- Payload transitions to `IDLE`

### Fault handling

- Invalid configuration → `ERR`, no state change
- Runtime fault → `STATE ERROR`
- Serial timeout → GUI alerts the operator

---

## 14. Build Guidelines

### Firmware (Nano)

- Line-based command parser
- Explicit internal state machine
- Non-blocking serial reads
- Defensive input validation
- Clear and consistent error reporting

### Python Application

- Never block the GUI thread
- Always wait for `ACK` or `ERR` responses
- Guard against serial disconnects
- Validate inputs before sending commands
